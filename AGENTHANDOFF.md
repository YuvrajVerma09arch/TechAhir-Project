### 2.3 Engine / ML
- Modular engine returning structured predictions with separate category/priority confidence,
  `requires_human_review`, `review_reason`, `status`.
- **No ground-truth labels exist** → do NOT pretend to train a supervised classifier. Implement a
  transparent, conservative deterministic baseline (keyword/feature rules + optional TF-IDF
  exemplar similarity if useful). Document limitations. Save/load nothing that implies training.
- Conservative confidence routing. Auto-accept only if BOTH category and priority thresholds pass.
  Never treat uncalibrated probability as reliable confidence — if unknown, review.
- Dedicated **priority safety layer**: security breach, account compromise, financial loss,
  outage, severe impact → urgency review. Never auto-downgrade a potentially critical ticket.
  If model and safety rules disagree → escalate. If ambiguous or prediction fails → escalate.
  Preserve escalation reason. Do not claim keyword detection alone determines urgency.

### 2.4 Failure handling
Never lose a ticket. Handle empty text, missing fields, duplicate ids, invalid formats, model
exceptions/timeouts/invalid output/missing confidence, recoverable DB failures. Distinct states:
`auto_classified`, `pending_review`, `human_reviewed`, `failed`. Batch processing idempotent.
Treat ticket text as **untrusted data** — planted prompt injections exist (see §2.6).

### 2.5 API (Pydantic validated) + Dashboard sections
Endpoints: `POST /api/triage/batch`, `GET /api/tickets` (filter by category/priority/status,
paginated), `GET /api/tickets/{ticket_id}`, `GET /api/review-queue`, `POST /api/review/{ticket_id}`,
`GET /api/report`, `GET /health`. Consistent error format, validation at boundaries.

React dashboard sections (all metrics from real stored records):
- **A. Overview** — total, processed, auto-classified, pending review, human-reviewed, failed.
- **B. Priority analytics** — counts per priority (Low/Medium/High/Urgent) + chart.
- **C. Category analytics** — distribution by category + category×priority breakdown.
- **D. Human review queue** — searchable table, indicators, confidence, reasons, review modal
  with editable category/priority, mark reviewed.
- **E. Reports** — processing summary, automation coverage, review rate, failure rate, CSV exports.

Design: modern SaaS, light theme, professional blue/indigo accent, clean typography, WCAG AA,
no "AI aesthetic", responsive, real empty/loading/error states, semantic tokens.

### Decision log — external AI/LLM API (2026-11-21, user asked for a decision)
**DECIDED: NO external LLM API call in this submission.** The deterministic rules layer remains the
first-pass engine. Reasons: (1) master prompt §3 forbids paid APIs, API keys and external model
services — the reviewer must run it offline; (2) reproducibility of the published results;
(3) the dataset contains planted prompt injections aimed at an AI classifier, so an LLM primary
classifier would put the attack on the critical path; (4) no labels exist to prove an LLM is better,
and its self-reported confidence is uncalibrated (explicitly warned against in the brief).
Retained from the user's proposal: call it the **rules layer / first-pass engine** (not "model");
keep TF-IDF out of the story; keep the design **LLM-ready** via the existing `TriageEngine` protocol
and document an LLM as a future extension in the design note; keep failure handling real via
injectable failing/invalid engines and tests. README §1, §6 and §11 updated accordingly.
